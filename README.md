# 333 Watcher

333 Watcher 是一款隐私优先的 Chrome 网页变化监控扩展。它可以监控整页内容，也可以只监控页面中的某个文字、链接或图片地址；发现变化后，通过 Chrome 通知提醒你。

项目地址：<https://github.com/lijianbin2/333watch>

当前版本：**v0.6.44**

Chrome Web Store 扩展 ID：`gaakbhfclmmeholfdahnpkocdipijndo`

## 为什么使用 333 Watcher

- **监控范围明确**：可以监控整页，也可以只盯一个价格、库存、标题、下载链接或跳转地址。
- **减少误报**：元素和链接变化会进行二次确认，临时页面抖动不会立即触发通知。
- **多设备同步**：监控配置、提醒历史和已读状态可随 Chrome 账号同步。
- **跨设备去重**：在 A 电脑读过同一事件后，其他电脑同步到已读状态时不会再次弹出相同提醒。
- **本地隐私优先**：没有广告、统计、跟踪器或项目自建服务器。

## 功能

| 功能 | 说明 |
| --- | --- |
| 整页监控 | 获取网页 HTML，移除注释、脚本、样式和 `noscript` 后比较内容指纹 |
| 元素文字 | 监控指定 CSS 元素的最深叶子文字 |
| 元素链接 | 监控元素的 `href` 或 `src`，相对地址会转换为绝对地址 |
| 定时检查 | 使用 `chrome.alarms` 调度，支持每 1–10,080 分钟 |
| 立即检查 | 可在扩展面板中手动触发单条监控 |
| 变化提醒 | 显示旧值和新值，并写入可管理的历史记录 |
| 失效与恢复 | 连续失败达到阈值后提醒，监控恢复后再次提醒 |
| 跨设备同步 | 配置、提醒历史和已读状态保存在 `chrome.storage.sync` |
| 配置导入导出 | 通过 JSON 在设备或配置文件之间迁移监控 |
| 内置测试 | 使用虚拟文本和链接验证通知链路，无需访问真实网站 |

## 监控类型

### 整页

适合监控：

- 公告和新闻列表；
- 状态页和版本发布页；
- 商品或活动页面的整体改动；
- 页面中不方便精确定位的区域。

整页模式会忽略 HTML 注释、脚本、样式和 `noscript`，以减少不影响正文展示的改动造成的提醒。动态广告、轮播图或随机页面内容仍可能造成误报；这类页面建议改用元素监控。

### 元素文字

输入 CSS selector，监控目标元素的文字。扩展会优先使用最深的叶子节点，避免外层容器抢占匹配结果。

适合：

- 商品价格和库存状态；
- 公告标题和发布时间；
- 按钮文字、状态标签和计数；
- 页面中唯一且稳定的文本。

### 元素链接

输入 CSS selector，监控元素的 `href` 或 `src`。页面使用相对路径时，扩展会按监控页面的 URL 转换为绝对地址后比较。

适合：

- 下载文件地址；
- 跳转按钮目标；
- 版本安装包或镜像链接；
- 图片资源地址。

2. 核对扩展 ID：

   `gaakbhfclmmeholfdahnpkocdipijndo`

### 从源码加载

1. 打开 `chrome://extensions/`。
2. 开启“开发者模式”。
3. 点击“加载已解压的扩展程序”。
4. 选择本仓库的 `333-watcher` 目录。
5. 将 333 Watcher 固定到浏览器工具栏。

## 快速开始

### 监控整页

1. 打开需要监控的网页。
2. 点击工具栏中的 333 Watcher。
3. 选择“整页”。
4. 填写名称、URL 和检查间隔。
5. 点击“保存监控”。

新建监控的第一次成功检查只建立基线，不发送提醒。之后检测到内容变化时才会通知。

### 监控指定元素

1. 打开包含目标元素的网页。
2. 在扩展面板中选择“指定内容”。
3. 点击“选择网页元素”。
4. 在页面上点击目标元素。
5. 选择监控文字、`href` 或 `src`。
6. 填写名称和检查间隔后保存。

修改监控的 URL、选择器或属性后，下一次成功检查会重新建立基线。

### 立即检查

在监控列表中点击“检查”，扩展会立即执行一次检查。元素或链接监控还会再次抓取页面确认新值稳定后才发送提醒。

## 管理提醒

扩展面板中的提醒历史支持：

- 查看最近提醒；
- 展开单条历史；
- 标记全部为已读；
- 清除已读历史。

### 跨设备去重规则

每次变化使用稳定事件标识，并带有同步递增的序号。不同状态即使后来再次出现，也会被识别为新的事件；相同事件则不会因为页面从 A 变化到 B、之后又变化回 A 而被错误去重。发送前会先在同步历史中写入短期事件认领，另一台设备看到认领后不会再次发送同一事件。

当一条提醒已在任意设备标记为已读后，其他设备收到同步状态时会跳过该事件。Chrome 同步并非实时锁：如果两台电脑在同一瞬间同时检查、且提醒尚未被任何设备读到，两台电脑仍可能各发送一次。

已读提醒保留 7 天，之后由扩展自动清理。清除已读历史会删除这些已读事件记录。

## 检查与容错

### 二次确认

元素文字、链接和下载地址变化后，扩展会使用 `cache: no-store` 再抓取一次。只有第二次读取仍得到相同新值时才发送提醒，减少 CDN 缓存、A/B 测试或页面抖动造成的误报。

### 元素选择器自愈

如果原 selector 失效，扩展会在当前页面中按上次文字或地址尝试找回元素，并更新 selector。找不到时不会把一次抓取失败直接当作内容变化。

### 失效提醒

连续检查失败达到 2 次后，监控会标记为失效并发送提醒。后续成功检查会清除错误状态并发送恢复提醒。

### 响应限制

- 单次请求超时：20 秒；
- HTML 响应上限：2.5 MB；
- JSON 响应上限：512 KB；
- DOM 扫描上限：50,000 个节点；
- 文字监控值：最多保存 4,096 个字符；
- 链接监控值：最多保存 2,048 个字符；
- 提醒历史：最多 50 条，并控制在 7 KB 以内。

## 隐私

333 Watcher 不包含广告、统计或第三方分析代码。

扩展会：

- 仅请求用户主动添加的监控 URL；
- 在浏览器扩展环境中保存监控配置和提醒历史；
- 使用 `chrome.storage.sync` 在用户的 Chrome 账号设备间同步这些数据；
- 在用户主动拾取元素时读取当前页面信息。

扩展不会：

- 上传监控配置到本项目服务器；
- 收集浏览历史、账号信息或使用统计；
- 在用户配置之外请求网页；
- 包含广告、跟踪器或分析 SDK。

更多内容见 [PRIVACY.md](./PRIVACY.md)。

## 权限说明

| 权限 | 用途 |
| --- | --- |
| `storage` | 保存监控配置、提醒历史和已读状态 |
| `notifications` | 发送变化、失效和恢复提醒 |
| `alarms` | 定时执行检查任务 |
| `activeTab` | 在用户主动操作时访问当前页面 |
| `scripting` | 注入元素拾取脚本 |
| `offscreen` | 在受限 DOM 环境中解析监控页面 |
| `<all_urls>` | 访问用户主动添加的 HTTP/HTTPS 监控地址 |

`<all_urls>` 是通用网页监控所需的权限。扩展不会主动扫描或访问未配置页面。

## 故障排查

### 没有收到通知

1. 确认 Chrome 系统通知和网站通知权限未被关闭。
2. 打开扩展面板，点击“检查”手动验证。
3. 检查监控是否已经处于失效状态。
4. 确认目标 URL 无需登录、不会返回 403，或在监控前先登录目标网站。
5. 检查 Chrome 是否开启了省电、冻结或休眠后不运行扩展的限制。

### 元素监控经常失效

- 优先选择稳定、唯一的 selector；
- 避免依赖随机生成的 class 名；
- 动态内容尽量监控稳定的 `data-*` 属性对应元素；
- 目标文字频繁变化时，扩展可能自动更新 selector，但仍应检查网页结构。

### 整页监控误报

整页模式可能受到广告、轮播、时间戳和随机内容影响。优先改用元素文字或元素链接监控。

### 同步没有立即生效

`chrome.storage.sync` 依赖 Chrome 账号和网络状态。离线设备只能在恢复网络后同步；同一瞬间发生的检查仍可能短暂重复。

## 更新日志

### v0.6.44

- 修复**元素自愈的文本查找把模糊匹配当成了比精确匹配更强的候选，可能永久把 selector 指到错误元素上**。
  - 背景：`offscreen.js` 的 `find-by-value` 文本分支在单遍扫描里让**模糊候选一命中就立即
    `return`**，排在后面的**精确匹配**（`t === target`）根本没有任何机会被比较。
  - 危害：页面前部常有包含目标子串的导航/提示文案（`下载 4.0.6.19 版本`），真正的目标叶子
    （`<span>4.0.6.19</span>` 或文件名元素）在文档后部。自愈会把 selector 写到前面那个提示
    元素上并**永久保存进 `monitor.selector`** —— 首次检查立刻拿错元素和基线比对、误报一次
    「已变化」，而真目标后续怎么变都不会被发现。这正是代码注释反复警告的「自愈盯错元素」
    类 bug。
  - 修法：改为单遍扫描收集三类候选（精确叶子 / 精确容器 / 模糊叶子）、最后统一决策，
    优先级 **精确叶子 > 精确容器 > 模糊叶子**，结果**与文档顺序无关**。保留 `target.length < 80`
    的长度闸门和「模糊只接受叶子节点」的约束，`MAX_SCAN_NODES` 单次扫描语义不变。
  - 测试：`tests/offscreen-review.test.cjs` 新增 `find-by-value` 文本分支的最小 DOM 桩回归
    （模糊在前/精确在前两种文档顺序都指向精确节点、无精确时模糊仍可用、仅容器精确时容器兜底、
    长文本仍不做模糊匹配）。已反向验证：还原旧逻辑后「模糊在前」那组必然失败。

    监控共用一个 alarm（`syncAlarms` 只建得出一个 → 其中一条**再也不会被检查**）、
    共用同一个通知 id（后一条直接顶掉前一条 → 用户看到"少了一条提醒"），且
    `findIndex(m.id === ...)` 永远只命中第一条 → **基线写到错的监控上**。

### v0.6.42

- 修复**上一版自己引入的回归：过期的检查结果反馈会「复活」**。
  - 现象：手动点过一次「立即检查」之后，那条结果（例如「未找到目标」「网络请求
    失败」）会被永久记住。此后任何一次无关的列表重建 —— 编辑某条监控、删除某条
    监控、开合测试面板、甚至重开弹窗的首屏渲染 —— 都会把那条早已过时的反馈重新
    贴回界面上。
  - 根因：v0.6.41 为了躲开 `renderList` 的并发竞态，刻意**不提前清空**
    `pendingCheckFeedback`，指望「后完成的那一轮」也会读到同一个标记。但这个标记
    因此永远不会被消费，一旦设置就残留到本次弹窗会话结束。
  - 修复：给 `renderList` 加一条 promise 链（`_renderChain`）把所有重建**串行化**，
    使「最后发起的那一轮」必然就是「最后落地的那一轮」，不再有后完成的轮次去冲掉
    已贴好的结果。串行化之后「贴回它的那一轮」就是最终结果，因此可以安全地在贴完
    之后把标记清空，从根上断掉残留。
  - 行为保持：`renderList()` 仍然返回 promise，原先 `await renderList()` 的调用方
    语义不变；不 await 的调用方（init 首屏、检查结果、增删改、测试面板）依旧正常。
- 测试：
  - 新增「陈旧反馈不得复活」回归测试：`检查 → 无关重建` 两步，断言第二轮之后旧
    反馈不再出现。已用 `git stash` 验证修复前必然失败。
  - 顺手修正测试 DOM 桩的一个保真度缺陷：桩里 `innerHTML = ''` 原先只是赋值，
    不会清空 `children`，导致旧节点一直留在列表里 —— 这恰好会把本该被发现的
    「陈旧反馈复活」bug 藏起来。现在按真实 DOM 语义清空。

### v0.6.41

- 修复**「立即检查」的检查结果反馈一闪即逝，点完什么也没看到**。
  - 根因：`checkNow()` 先 `showCheckFeedback()` 把结果写进 DOM 节点，紧接着
    `renderList()` 执行 `listEl.innerHTML = ''` 并重建每一行（新行的 feedback 一律
    `hidden`）。7 条结果分支里有 6 条是「先写反馈、再重建」，消息在用户看到之前
    就随旧节点一起被删掉了 —— 连「未找到目标」「网络请求失败」这类**必须让用户
    知道的错误提示**也一起消失。
  - 深层原因：反馈只在**建行过程中**贴回是不够的。`renderList` 是 `async` 且调用方
    **不 await** 它，init 的首屏渲染、检查结果、删除等会并发触发多轮重建；先完成的
    那轮即使贴上了反馈，也会被后完成的那轮 `innerHTML=''` 整片冲掉。
  - 修复：把反馈改为在本轮**建完所有节点之后**再按监控 id 贴（`li.dataset.monitorId`），
    且**不提前清空**标记 —— 后完成的那一轮读到同一个标记，照样会贴上。
    非目标行的旧反馈同时被清掉，避免"结果串到别的监控上"。
- 测试：新增 `checkNow` 回归测试，用会重复返回同一实例的 DOM 桩跑完整
  `check-now → renderList` 流程，断言重建后的行里反馈仍可见且文案正确。
  已用 `git stash` 验证修复前必然失败（实际值为空字符串）。

### v0.6.40

- 修复**popup 打开时清理历史，会把后台正在投递的在途通知认领一起抹掉，导致提醒被静默吞掉**
  （用户表现为「页面明明变了却没有提醒」）。
  - 根因：`history` 是整键读-改-写。popup 与 background 是**两个 JS 上下文**，
    `withHistoryLock` 只是进程内互斥，跨上下文完全无效。`add-monitor.js` 的 `pruneHistory()`
    拿本页旧快照裁剪后**整键写回**，会连带覆盖掉后台刚写入的**在途认领**（`pending` 条目）。
  - 后果链路很隐蔽：认领消失后 `arbitrateClaim` 找不到自己的记录，判定"可能已被别人投递"
    → 返回 `'skip'` → **既不发通知，也不报错**。这跟"没检测到变化"表现完全一样，很难排查。
  - 修复：新增 `prune-history` 消息处理器，popup 的裁剪统一交给 background 在
    `withHistoryLock` 内执行；background 不可用时才退回本页直裁剪。

- 修复**旧版链接监控在链接文本/地址含 HTML 实体时必然失效**的问题。

- 导入时保留 `eventSeq`：它参与跨设备去重 `eventKey` 的计算，一律重置为 0 会让导入后的监控与 `history` 里的旧事件撞上同一个 key，导致本该发送的提醒被误吞；
- 新增 `tests/add-monitor-review.test.cjs`：用最小 DOM 桩把弹窗脚本整个加载起来，直接对其纯函数做断言（链接监控不丢、`targetHref`/`targetText` 保留、`eventSeq` 保留、`interval` 夹紧、无效记录仍被拒）。已验证"旧版链接监控被丢弃"这一断言在修复前失败；
- 新增 `scripts/test.ps1`：一次跑完四个源文件的语法检查与全部测试套件。

### v0.6.29

- 修复开机补检"一个监控出错、后面全部不检查"：启动时会补检所有已逾期的监控。原实现直接在 `for` 循环里 `await checkMonitor(m)`，任何一次抛错都会中断整个循环——排在后面的逾期监控在这次开机里被静默跳过，要等下一个周期才被发现。现在每个监控独立 `try/catch`，单个失败只记日志、不影响其余监控；
- 修复通知链路的异常冒泡：提醒要写 `history` 才能跨设备去重，这一步遇到配额不足或离线会抛错，而 `checkMonitor` 此前没有兜底，异常会一路冒泡出补检循环。基线此时已经落盘、检测已算完成，这次变化下个周期不会再被判定——漏掉的提醒无法自动补回，但因此跳过其余所有监控的代价大得多，所以新增 `safeNotify()` 统一兜住发送/恢复/失效三类提醒的异常，只记日志；
- 定时闹钟回调同样补上 `try/catch`，避免 service worker 里出现无上下文的未捕获 rejection；
- 新增两组回归测试：一组让 `history` 写入抛配额错误（模拟通知必然失败），一组让单个监控的 `checkMonitor` 直接抛错，均断言其余逾期监控仍完成补检。已验证两组用例在修复前都会失败。

### v0.6.28

- 修复抖动回写导致基线倒退、进而重复提醒的问题：为了过滤 CDN / A-B 测试 / 缓存抖动造成的误报，链接与元素类监控在判定变化后会立刻二次抓取确认，两次结果不一致就按"抖动"处理、不发通知。原实现把二次抓取到的值无条件写回基线；但这期间别的设备（或本机下一轮）可能已经把基线推进到更新的值并已据此发过通知，无条件写回就会把基线**倒退**到旧值——同一次变化于是被反复判定成新变化。现改为 compare-and-set：只有存储里的基线仍等于本轮刚写入的那个值时才回写，否则跳过；
- 新增对应回归测试：模拟"第一次抓取 A → 判定变化并落盘 → 二次抓取 B → 判定抖动"，同时让另一台设备在这期间把基线推进到 C，断言回写被跳过、基线保持 C、不发通知。已验证该用例在旧的"无条件回写"实现下会失败（基线会被写回 B）；
- 该修复配合已有的跨设备认领仲裁，共同消除"换电脑后收到重复提醒"的最后一条触发路径。

### v0.6.27

- 修复迁移失败导致的数据丢失：旧版数据迁移时，代码先把 `watchers` 旧键删掉，再写新的 `monitors`。一旦写入遇到配额不足（例如监控过多、超出 Chrome 每项 8KB / 总量 100KB 上限），迁移会中断，而旧数据已经被删掉——旧监控既没迁移成功、也再也找不回来。现在改成**写入成功后才清理旧键**：写失败时旧数据原样保留，下次启动可重试迁移；
- 新增对应回归测试（模拟写入抛配额错误，断言 `watchers` 仍然存在、`monitors` 未被写入；以及迁移成功后旧键被正确清理）。已验证该用例在旧的"先删后写"实现下会失败；
- 清理未使用的常量 `FOREIGN_DEVICE_LOOKBACK_MS`（多设备判定改用心跳表后已不再需要）。

### v0.6.26

- 修复换设备后重复收到同一条提醒：`storage.sync` 是最终一致的，A 电脑写下的认领要经过同步传播才可能被 B 电脑读到。原实现固定等 600ms 只读一次 `history`，传播稍慢时两台设备都只看到自己的认领，于是同一次变化各发一条一模一样的通知。现改为在仲裁窗口内持续轮询——看到对手就立刻按 `claimAt` + `id` 全序仲裁决定输赢，赢家不用等满窗口，输家撤回自己的认领；
- 仲裁窗口长度按“是否真的存在多台设备”自适应：新增设备心跳（`storage.local` 里的本机 ID + `storage.sync` 里的心跳表，30 分钟写一次、24 小时过期），单设备仍是 600ms 快速路径，多设备才放宽到 5s。心跳只决定窗口长短，不参与去重，读改写竞争无害；
- 心跳写不进去（配额/离线）时按多设备处理：窗口拉长只会晚几秒，不会漏发通知；
- 认领期间自己的认领若被整键覆盖或清理，仲裁直接判定跳过，避免发出无法追溯的重复通知；
- 测试改为虚拟时钟驱动（`setTimeout`/`Date.now` 都由时钟泵推进），5 秒仲裁窗口不再拖慢单测，并新增“对手认领在窗口中途才同步过来必须撤回自己”“单设备窗口不得被拉长”“多设备窗口确实拉长”“认领消失/输给更早对手”四组用例（已验证这组用例在旧的固定 600ms 实现下会失败）。

### v0.6.25

- 修复监控列表的整键读-改-写竞争：`storage.sync` 的 `monitors` 是一个键，后台定时检查与 popup 的增删改、导入、迁移并发时后写者会整键覆盖先写者（丢监控，或把刚写入的检查基线回滚成旧值从而重复通知）。现所有写入统一走 background 的进程内互斥锁 + `mutateMonitors()`；
- popup 不再直接写 `monitors`，新增 `mutate-monitors` 消息通道（upsert / remove / set-interval / import-by-key），由 background 基于存储里的最新列表执行；无法通信时（如本地预览）才回退到页面直写；
- upsert 按 `monitorKey` 兜底去重：页面侧新增去重读的是旧快照，并发下也不会建出两条相同监控；
- 监控被删除后写入落空时返回 `deleted` 而非 `error`；
- 修复跨设备并发认领的残余重复通知：`storage.sync` 是整键后写覆盖，两台设备的 pending 认领可能同时存在。现按 `claimAt` + `id` 做确定性仲裁，只有赢家发送，输家撤回自己的认领；
- 所有 `history` 写入统一走进程内互斥锁，认领、投递确认、清理、标记已读串行化，避免并发写互相覆盖丢记录；
- popup 的「标记已读 / 全部已读」改为发给 background 处理，不再由页面直接整键覆写 `history`；
- 修复未读过滤条件 `!h || !h.pending` 会保留 `null` 记录、随后 `h.read` 抛 `TypeError` 的崩溃路径；
- 清理 `history` 中的 `null` / 非对象记录，标记已读不再误改未完成投递的认领；
- 检查结果基线写不进同步存储时不再发通知（否则会留下无法追溯的误报），并释放检查锁让下个周期重试；
- 失败计数写入失败时记录日志，不再静默吞错；
- 选择器「重新选择」时清除 `pendingPick`，避免下次打开 popup 回填已放弃的陈旧选择；重复注入选择器时摘掉 `runtime.onMessage` 监听器，避免监听器泄漏；
- 新增认领仲裁、并发写入不丢记录、标记已读保护认领、监控列表互斥写入、`mutate-monitors` 通道、存储写失败不通知的测试。
